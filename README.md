# Earthquake Pipeline

A batch data pipeline that extracts earthquake events from the USGS API, moves them through a Bronze/Silver/Gold lakehouse pattern, and loads a Snowflake star schema for analytics.

## Architecture

```
USGS API --> Bronze (raw JSON) --> S3 --> Silver (Parquet) --> S3 --> Snowflake (Star Schema)
             data/bronze/           |       data/silver/        |      gold.dim_date
                                     |       (PySpark transform) |      gold.dim_location
                                     |                           |      gold.dim_magnitude_band
                                     v                           v      gold.fact_earthquake
                              s3://<bucket>/bronze/        s3://<bucket>/silver/
```

Each stage is a standalone script (extract, upload, transform, load) wired together by `src/pipeline.py`, which also handles multi-day backfills.

## Tech Stack

- **Python** — pipeline scripts, orchestration
- **PySpark** — Bronze → Silver transform, partitioned Parquet writes
- **boto3** — S3 uploads for Bronze and Silver
- **Snowflake** (`snowflake-connector-python`) — Gold star schema warehouse
- **pytest** — tests against the live USGS API

## How to Run

### Setup

```bash
cd earthquake-pipeline
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

### Environment variables

| Variable | Used for |
|---|---|
| `S3_BUCKET` | Bronze/Silver upload destination |
| `SF_ACCOUNT` | Snowflake account identifier |
| `SF_USER` | Snowflake username |
| `SF_PASSWORD` | Snowflake password |

```bash
export S3_BUCKET=your-bucket-name
export SF_ACCOUNT=your-account-id
export SF_USER=your-username
export SF_PASSWORD=your-password
```

(Snowflake warehouse/database/schema — `earthquake_wh` / `earthquake_db` / `gold` — are fixed in `src/warehouse/create_tables.py` and `src/warehouse/load_gold.py`.)

### One-time: create the Gold schema

```bash
python3 -m src.warehouse.create_tables
```

### Run the pipeline

Single day:

```bash
python3 -m src.pipeline --start 2026-01-01 --end 2026-01-02
```

Multi-day backfill (loops one day at a time; a failed day is logged and skipped, not fatal):

```bash
python3 -m src.pipeline --start 2026-01-01 --end 2026-01-05
```

### Run the tests

```bash
pytest tests/ -v
```

## Star Schema

**dim_date**
| Column | Type |
|---|---|
| date_key (PK) | INTEGER |
| full_date | DATE |
| year | INTEGER |
| month | INTEGER |
| day | INTEGER |
| day_of_week | VARCHAR |

**dim_location**
| Column | Type |
|---|---|
| location_key (PK, AUTOINCREMENT) | INTEGER |
| place | VARCHAR |
| latitude | FLOAT |
| longitude | FLOAT |
| region | VARCHAR |

**dim_magnitude_band**
| Column | Type |
|---|---|
| magnitude_band_key (PK) | INTEGER |
| band_name | VARCHAR |
| min_magnitude | FLOAT |
| max_magnitude | FLOAT |

**fact_earthquake**
| Column | Type |
|---|---|
| earthquake_key (PK, AUTOINCREMENT) | INTEGER |
| usgs_id | VARCHAR |
| date_key (FK -> dim_date) | INTEGER |
| location_key (FK -> dim_location) | INTEGER |
| magnitude_band_key (FK -> dim_magnitude_band) | INTEGER |
| magnitude | FLOAT |
| depth_km | FLOAT |
| tsunami | INTEGER |
| event_time | TIMESTAMP |
| updated_time | TIMESTAMP |

## What I Learned

- The USGS API's documented `metadata.count` field disappears from the response the moment you pass `limit`/`offset` — I had to verify that against a real response instead of trusting the field would behave the same way during pagination, and switch to a "short page means last page" stopping condition instead.
- Retry logic needs to distinguish failure types: a 4xx means my request is wrong and retrying won't help, but a 5xx or timeout is transient and worth retrying with exponential backoff so I'm not hammering a struggling server at a fixed rate.
- Idempotency in the warehouse comes from `MERGE`, not `INSERT` — and because surrogate keys like `location_key` are generated by Snowflake itself, the fact table's foreign key lookups have to be resolved with a SQL join inside Snowflake, not computed ahead of time in Python.
- A partitioned Spark write with `mode("overwrite")` replaces the *entire* output directory by default, not just the partitions being written — something that only became a real problem once I started backfilling multiple days instead of running the pipeline once.
- Orchestrating multiple days of a pipeline is really about where you put the `try`/`except`: wrapping each day's run individually (instead of the whole backfill) is what lets one bad day fail loudly without losing progress on every other day.
